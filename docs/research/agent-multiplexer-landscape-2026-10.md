# Agent-multiplexer landscape (2026-10-21)

## Scope and confidence

This is a product and capability comparison, not a benchmark or hands-on usability test. Claims about other products below come from their official docs or repositories, checked on 2026-10-21. Product documentation describes intended behavior; it does not independently prove reliability. Seshi claims are checked against this repository's README, `docs/agent-status.md`, `docs/features/fleet/intent.md`, and current implementation/docs. “Gap” means a candidate area to validate or improve, not an assertion that Seshi lacks the capability entirely.

There was no existing `docs/research/` convention, so this note creates that directory for this one research report.

## Executive take

Seshi already has a strong and unusually broad foundation: a cross-platform, daemon-owned terminal multiplexer; agent status and attention; worktrees; persisted sessions and output; subagent visibility where hosts expose lifecycle data; a commander/fleet mode; and scriptable CLI/MCP surfaces. Its highest-value opportunity is to make these capabilities feel dependable and easy to understand across machines and providers, rather than reintroducing a general workflow/profile engine that was deliberately removed.

The competitive pattern is clear: the best products treat **status truth and attention routing as the core product**, then add useful control surfaces around that truth. Herdr exposes agent-aware commands and remote machines; Nebula invests heavily in native hook coverage, explicit unread/completion states, and a built-in orchestrator; Fut offers native lifecycle integrations and focus-preserving machine-readable agent commands; cmux pairs notification state with a powerful CLI/control API and, in its Cloud product, remote durable workspaces. These are useful reference points, but not all are direct substitutes for Seshi's Windows-first, cross-platform TUI.

## What the official sources establish

### Herdr

Herdr distinguishes workspace, tab, pane, agent and server session; panes survive client detach, splits work both directions, and its UI is explicitly mouse-native. Agent states include `unknown`, which is a useful precedent for presenting uncertainty rather than guessing. ([Concepts](https://herdr.dev/docs/concepts/))

The automation interface goes beyond a basic multiplexer: a script or agent can start a recognized agent in an existing shell pane, prompt it, wait for state, read output and interact with a blocked prompt. The docs show recipes for each. ([Agent automation](https://herdr.dev/docs/agent-automation/), [CLI reference](https://herdr.dev/docs/cli-reference/)) Herdr also documents local UI attaching to remote servers over SSH, as well as saved machines. ([Persistence and remote access](https://herdr.dev/docs/persistence-remote/))

### Nebula

Nebula has the richest status vocabulary in this group and explicitly distinguishes a completed-but-unseen turn from a read completion. It installs managed hooks for supported CLIs at spawn, preserves user hook data, and uses a PTY progress scanner for a cancellation edge case. Its docs explicitly disclose provider limitations where permission or lifecycle hooks are unavailable. ([README](https://github.com/AgentSystemLabs/nebula), [how it works](https://github.com/AgentSystemLabs/nebula/blob/main/docs/how-it-works.md))

Nebula also builds orchestration directly into the application: a pinned orchestrator can list, read, message and spawn sessions. This validates that some users value a control agent, but its own README cautions that the project is work in progress, fast changing, and tailored to its maintainer. ([README](https://github.com/AgentSystemLabs/nebula))

### Fut

Fut makes provider lifecycle integration explicit and supplies focus-preserving JSON commands to list/get agents, prompt, wait and read. Its docs make a practical distinction: native lifecycle reports are more reliable than screen fallbacks, while Codex requires an additional documented notification setting for authoritative completion. ([Agent activity](https://fut.sh/agents/), [Codex integration](https://fut.sh/agents/codex/))

Its project catalog is explicit and avoids filesystem scanning; projects can refer to trusted recipes, and path/recipe preparation runs in the background with cancellation before the open request is sent. This is a focused onboarding/workspace feature rather than a general workflow runner. ([Projects](https://fut.sh/projects/))

### cmux

cmux TUI documents cross-platform workspaces, screens, split panes, terminal/browser tabs, headless attach, SSH machines and a control socket; terminal actions and state inspection are available to scripts. ([cmux TUI](https://cmux.com/docs/tui)) The macOS notification system has a full unread/read lifecycle and suppression rules, with event metadata that can distinguish subagent completion. ([Notifications](https://cmux.com/docs/notifications)) cmux Cloud adds remote durable terminals, preconfigured agent hooks and remote project/agent commands, but that is a broader cloud-workspace product and should not be treated as a direct local-TUI comparison. ([Cloud workspaces and agents](https://cmux.com/docs/cloud/workspaces))

## Candidate improvements for Seshi

These are research-backed opportunities for discussion, not approved roadmap changes. They should be ordered by the Seshi mission (“never lose or misreport an agent”) rather than by feature count.

1. **Make status confidence and freshness unmistakable.** Herdr's explicit `unknown` and Nebula's `disconnected`/`terminated` states show useful ways to represent evidence gaps. Seshi already exposes status evidence and age; the opportunity is to make stale hooks, exited processes, uncertain detection and host limitations visible in the main sidebar without implying that an agent is still active. Treat this as a cross-provider correctness project, not another color or spinner pass.
2. **Make setup self-verifying and repeatable on every machine.** Seshi now has `doctor` and provider integrations, including machine-local Codex hook checks. Fut's “doctor” and bundled, version-matched agent instructions plus Nebula's spawn-managed hooks are useful onboarding patterns. A possible next step is a per-provider doctor matrix that distinguishes installed, loaded (requires restart), live, fallback-only and unsupported capabilities, with a safe repair command. Keep per-machine configuration explicit; do not assume it syncs with Seshi settings.
3. **Treat attention as a complete lifecycle.** Nebula and cmux explicitly separate unread completion from read completion and suppress attention noise when the user is already looking. Seshi already has needs-you/done and recently made completion quiet. Validate whether unread state is consistent across multiple Seshi clients, subagent completion and reopen/recovery; only invest in new badges or notifications if a measured gap remains.
4. **Give subagent rows a truthful, compact contract.** Seshi's host-dependent subagent discovery is a real differentiator, but labels and liveness depend on source metadata. Keep rows task-named when supplied, explain when a name is inferred, and distinguish live from finished/unconfirmed; test stop/exit/crash paths across providers. Do not promise direct messaging or introspection when the host doesn't expose it.
5. **Strengthen automation primitives without rebuilding the workflow engine.** Herdr and Fut demonstrate value in stable JSON operations for list/get/read/send/wait/focus, and Nebula shows a separate orchestrator experience. Seshi already has CLI/MCP/fleet capabilities. The opportunity is a consistent, scriptable event/state contract and better inspectability so external workflow tools can use Seshi as the durable terminal layer. Preserve the product decision to keep arbitrary pipelines, profiles and workflow ownership outside Seshi.
6. **Make session update/restart impact legible.** Each daemon-backed product has a different update lifecycle; Herdr documents that stopping the server exits pane processes, Fut defers daemon restart, and Nebula documents in-place restart. Seshi's update UI already distinguishes installed/window/daemon versions and restart pending. Continue to make the consequence and safe timing explicit; evaluate a seamless daemon handoff only if it can preserve running PTYs on all supported operating systems.
7. **Improve “what now?” discovery and reduce terminal UI learning cost.** Fut's project picker shows explicit project catalog behavior and asynchronous preparation; Herdr treats mouse interaction as first class; Nebula offers a guided walkthrough and project-first setup. Seshi could validate its first-run journey with new users, especially choosing a project, selecting/opening an agent, understanding leader shortcuts, and checking integrations. This is a research/test opportunity before building more screens.

## Strategic read

Seshi should not try to beat every neighbor on the number of built-in workflow features. Its clearest position is a **cross-platform, local-first control surface for persistent coding-agent sessions**, with truthful attention status, native worktree support, useful CLI/MCP automation and low-noise agent visibility. Research suggests two high-leverage differentiators to deepen: **trustworthy cross-provider lifecycle status** and **frictionless recovery/setup across machines**.

The likely product tradeoff is that Herdr/Nebula can expose deeper agent-specific APIs or orchestration on supported hosts, while Seshi's cross-platform scope and general terminal model are broader. Seshi should explain this boundary directly: the pane remains usable for any CLI, while exact status/helper visibility depends on the host integration. A small structured audit across real Claude, Codex, OpenCode and one hookless provider will be more informative than adding another orchestration screen.
